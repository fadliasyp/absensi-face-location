Bagian 1

Ringkasan Penelitian

Versi satu kalimat

Sistem ini mencatat kehadiran peserta dengan menggabungkan kecocokan identitas wajah, challenge gerakan wajah, validasi radius lokasi, kalender kerja, serta waktu server WIB agar data absensi lebih konsisten dan lebih sulit dimanipulasi dari sisi browser.

Latar belakang masalah

Identitas

Absensi biasa belum memastikan bahwa orang yang mengisi adalah pemilik akun.

Lokasi

Kehadiran perlu dibatasi pada titik dan radius yang ditetapkan organisasi.

Waktu

Status hadir, terlambat, dan alfa harus mengikuti jadwal yang konsisten, bukan jam perangkat.

Solusi yang dibangun

  • Face recognition: membandingkan descriptor wajah kamera dengan descriptor yang tersimpan pada profil.
  • Active liveness: peserta mengikuti tiga instruksi acak berupa kedip, tengok kanan, atau tengok kiri.
  • Geofencing: koordinat peserta dihitung jaraknya terhadap lokasi absensi memakai Haversine.
  • Kebijakan waktu: server menentukan kapan absensi dibuka, status Hadir/Terlambat, dan kapan Alfa dibuat.
  • Kalender kerja: Sabtu-Minggu libur secara default dan admin dapat memberi pengecualian per tanggal.
  • Pelaporan: admin memonitor data dan mengekspor laporan PDF atau Excel, termasuk tautan foto bukti.

Kontribusi implementasi

Kontribusi proyek bukan membuat algoritma pengenalan wajah baru. Kontribusinya adalah mengintegrasikan beberapa mekanisme verifikasi ke dalam satu alur absensi yang memiliki pembagian validasi client-server, riwayat, kalender, izin, dan pelaporan.

Kalimat presentasi: “Sistem tidak hanya bertanya siapa penggunanya, tetapi juga apakah ada respons gerakan langsung, apakah posisinya berada di radius yang diizinkan, dan apakah waktunya masih berada dalam jendela absensi.”

Mengapa aplikasi statis?

Arsitektur statis dipertahankan karena halaman dapat langsung berjalan di browser dan backend-as-a-service menyediakan kebutuhan auth, database, storage, serta function. Konsekuensinya, disiplin keamanan server tetap penting karena kode JavaScript browser dapat dilihat dan dimodifikasi pengguna.

Jawaban singkat jika ditanya framework: “Frontend tidak memakai React/Vue/Angular. Aplikasi menggunakan HTML, CSS, dan JavaScript murni. Supabase menjadi backend platform, sedangkan face-api.js dan MediaPipe adalah library pemrosesan wajah.”

Model face-api.js yang dimuat

Tiny Face Detector

Mencari area wajah pada frame kamera. Dipilih karena relatif ringan untuk browser.

Face Landmark 68

Mendeteksi titik-titik struktur wajah agar wajah dapat disejajarkan dan dianalisis.

Face Recognition Net

Mengubah wajah menjadi descriptor numerik dengan panjang 128 nilai.

Pendaftaran wajah

  1. Kamera depan dibuka dan satu wajah dideteksi.
  2. face-api.js menghasilkan descriptor 128 dimensi.
  3. Descriptor diubah menjadi array dan disimpan pada profiles.face_descriptor.
  4. Foto referensi disimpan pada bucket Supabase Storage foto-wajah.

Verifikasi wajah

Descriptor hasil kamera dibandingkan dengan descriptor profil menggunakan Euclidean distance. Semakin kecil nilainya, semakin dekat kedua representasi wajah.

d(p,q) = √Σ (pᵢ − qᵢ)²    untuk i = 1 ... 128
Implementasi proyek: cocok apabila distance ≤ 0,5. Pemeriksaan dilakukan sebelum challenge dan sekali lagi setelah challenge.
Makna threshold: threshold 0,5 adalah parameter implementasi, bukan jaminan universal. Idealnya dikalibrasi memakai data uji pengguna dan kondisi perangkat target.

Active Liveness Tahap 1

Tujuan

Liveness menambah hambatan terhadap penggunaan foto statis atau video yang tidak sesuai instruksi. Sistem meminta respons aktif sehingga pengguna tidak hanya menampilkan wajah.

Baseline singkat
→

→
Kembali netral
→
Instruksi 2 & 3
→
Cocokkan wajah akhir

Perilaku versi aktif

  • Terdapat tiga langkah acak dari aksi kedip, tengok kanan, dan tengok kiri.
  • Setiap langkah kedip hanya meminta satu kedipan; rangkaian minimal memuat satu langkah kedip.
  • Aksi yang sama tidak muncul dua kali berturut-turut.
  • Instruksi belum terlihat saat baseline dan jeda acak, sehingga replay lebih sulit dipersiapkan.
  • Tengok dinilai dari arah peserta, bukan arah tampilan layar yang dicerminkan.
  • Sistem menolak lebih dari satu wajah, wajah hilang, kamera berhenti, tab disembunyikan, atau gerakan terlalu dini/berlawanan.
  • Durasi inti tiap tantangan sekitar delapan detik dengan toleransi render singkat.

Fusion detector untuk kedip

face-api.js

Landmark mata menghasilkan perubahan rasio bukaan mata. Sinyal ini membantu membaca transisi mata terbuka–tertutup–terbuka.

MediaPipe FaceLandmarker

Blendshape eyeBlinkLeft dan eyeBlinkRight menjadi sinyal kedua agar kedipan cepat pada perangkat berbeda lebih mudah ditangkap.

Batas klaim akademik: ini adalah active liveness berbasis challenge di browser, bukan Presentation Attack Detection tersertifikasi. Sistem membantu menolak foto/video sederhana, tetapi tidak dapat dijamin melawan virtual camera, browser yang dimodifikasi, deepfake real-time, atau serangan replay canggih.
Jika ditanya mengapa challenge acak: video rekaman memiliki urutan gerak tetap. Instruksi acak, jeda acak, dan kewajiban kembali netral membuat rekaman yang sudah disiapkan lebih sulit mengikuti urutan real-time.

Geolokasi dan Geofencing

Teknologi lokasi

Browser meminta posisi melalui navigator.geolocation.getCurrentPosition() dengan enableHighAccuracy: true, maximumAge: 0, dan timeout 15 detik pada halaman peserta. Hasil utamanya adalah latitude dan longitude.

Alur validasi

→

→

→
Kirim ke RPC
→

Rumus Haversine

a = sin²(Δφ/2) + cos φ₁ · cos φ₂ · sin²(Δλ/2)
d = 2R · asin(√a),   R ≈ 6.371.000 meter

Rumus ini menghitung jarak terpendek di permukaan bumi dari dua koordinat. Browser memakainya untuk pengalaman pengguna, sedangkan fungsi database menghitung ulang agar keputusan tidak hanya bergantung pada angka dari UI.

Mengapa laptop kadang kurang akurat?

Laptop umumnya tidak memiliki GPS. Browser/Windows dapat memperkirakan posisi melalui Wi-Fi, alamat IP, jaringan, atau layanan lokasi sistem. Karena sumbernya berbeda, posisi dapat meleset walaupun pengguna sebenarnya dekat.

Bukan otomatis bug kode: enableHighAccuracy hanya permintaan kepada perangkat, bukan jaminan posisi GPS yang presisi.
Catatan audit: implementasi peserta saat ini mengambil satu pembacaan lokasi dan belum memakai nilai coords.accuracy untuk menolak atau mengulang pembacaan yang buruk.

Peningkatan yang dapat diajukan

  • Mengambil beberapa sampel posisi dan memilih pembacaan dengan akurasi terbaik.
  • Menampilkan estimasi akurasi kepada peserta.
  • Menolak atau meminta ulang apabila radius ketidakpastian terlalu besar.
  • Memberi panduan menyalakan Location Services dan Wi-Fi pada laptop.

Penting: peningkatan di atas adalah usulan pengembangan, bukan perilaku aktif yang boleh diklaim sudah tersedia.

Bagian 6

Logika Waktu, Kalender, dan Alfa

Timeline absensi dinamis

Terlalu AwalSebelum Jam Masuk − 1 jam
HadirDari waktu buka sampai Batas Masuk
TerlambatSetelah Batas Masuk sampai sebelum deadline
Ditutup / AlfaMulai Jam Generate Alfa

Contoh: Jam Masuk 09.00, Batas Masuk 11.00, Jam Generate Alfa 17.00. Absensi dibuka 08.00; pukul 08.00–11.00 berstatus Hadir; setelah 11.00 sampai 16.59 berstatus Terlambat; mulai 17.00 absensi ditolak dan peserta tanpa absensi/izin diproses menjadi Alfa.

Mengapa memakai waktu server?

Jam perangkat pengguna mudah salah atau dimanipulasi. Fungsi database menggunakan statement_timestamp() lalu mengonversinya ke Asia/Jakarta. Karena itu tanggal, waktu masuk, dan status tidak ditentukan oleh nilai yang dikirim browser.

Kalender kerja

KondisiKeputusan
Senin–Jumat tanpa overrideHari kerja.
Sabtu/Minggu tanpa overrideLibur default.
Override tanggal = liburLibur meskipun hari kerja biasa.
Override tanggal = masukHari kerja meskipun Sabtu/Minggu.

Generate Alfa

  • pg_cron menjalankan pemeriksaan setiap menit.
  • Fungsi hanya membuat Alfa setelah Jam Generate Alfa yang aktif.
  • Proses hanya berlaku pada hari kerja.
  • Insert bersifat idempoten: pemanggilan ulang tidak membuat duplikasi.
  • Fallback apabila deadline belum dikonfigurasi adalah pukul 12.00 WIB.
Perubahan jadwal pada hari yang sama: pengaturan dapat diubah admin. Data Hadir/Terlambat yang sudah tercatat tidak dihitung ulang. Jika deadline Alfa dimundurkan dan waktu server masih sebelum deadline baru, Alfa hari ini dapat dibuka kembali untuk pengajuan izin sesuai fungsi migrasi lanjutan.

B. Pendaftaran wajah

  1. Peserta membuka halaman pendaftaran wajah dan memberi izin kamera.
  2. Sistem mendeteksi satu wajah serta membuat descriptor 128 dimensi.
  3. Foto referensi diunggah dan descriptor disimpan pada profil.
  4. Session routing menganggap profil siap apabila data wajah dan foto tersedia.

C. Absensi

  1. Pre-check server: periksa hari kerja, jadwal, dan apakah data hari ini sudah ada.
  2. Verifikasi wajah awal: descriptor kamera dibandingkan dengan profil.
  3. Challenge liveness: jalankan tiga instruksi acak.
  4. Verifikasi wajah akhir: pastikan wajah setelah challenge tetap milik peserta.
  5. Ambil lokasi: browser meminta koordinat dan menentukan titik terdekat.
  6. Foto bukti: frame akhir dikompres dan diunggah ke R2 private.
  7. RPC pencatatan: server memvalidasi akun, waktu WIB, lokasi, radius, dan duplikasi.
  8. Hasil formal: popup menampilkan status Hadir/Terlambat atau alasan penolakan.

D. Izin manual

Peserta dapat mengajukan izin sakit/berhalangan dengan tanggal, keterangan, dan bukti. Server menolak izin pada hari libur, data ganda, tanggal yang sudah ditutup, atau setelah deadline dinamis. Izin yang sah menempati satu baris absensi pada tanggal tersebut.

Invariant utama: satu peserta hanya boleh memiliki satu data pada satu tanggal, baik Hadir, Terlambat, Izin, maupun Alfa.

Menghapus lokasi tanpa merusak riwayat

Relasi lokasi pada data absensi menggunakan ON DELETE SET NULL. Nama tempat disimpan sebagai snapshot pada baris absensi. Dengan demikian lokasi aktif boleh dihapus, tetapi riwayat absensi lama dan nama tempatnya tetap tersedia.

Privasi biometrik

Descriptor wajah bukan foto literal, tetapi tetap merupakan data biometrik sensitif karena dipakai untuk mengenali seseorang. Praktik yang perlu dijelaskan:

  • Batasi akses descriptor hanya untuk proses yang memerlukannya.
  • Jelaskan tujuan pengumpulan dan masa retensi kepada peserta.
  • Sediakan prosedur reset/penghapusan data wajah.
  • Jangan mencatat descriptor atau credential pada log publik.

Mengapa foto export dapat dilihat?

Bucket R2 tetap private. Export membuat tautan menuju public viewer yang kemudian menghasilkan signed URL sementara (sekitar lima menit). Keputusan produk ini membuat penerima laporan dapat membuka foto tanpa login, tetapi siapa pun yang memegang tautan viewer memiliki kemampuan sementara untuk mengakses foto tersebut.

Jawaban jujur: akses foto export adalah trade-off antara kemudahan verifikasi laporan dan privasi. Kontrol utamanya adalah object key yang sulit ditebak serta signed URL berumur pendek; tautan laporan tetap harus dibagikan secara terbatas.

Bagian 10.2

Latihan Pertanyaan Penguji I

1. Apakah Anda membuat model face recognition sendiri?

Tidak. Saya menggunakan model pralatih yang disediakan face-api.js. Kontribusi saya berada pada integrasi pendaftaran descriptor, pencocokan identitas, liveness, geolokasi, aturan waktu, database, dan pelaporan.

2. Mengapa memilih face-api.js?

Library ini dapat berjalan langsung di browser, menyediakan deteksi wajah, landmark, descriptor, dan perhitungan yang diperlukan, sehingga sesuai dengan arsitektur web statis proyek.

3. Apa yang disimpan dari wajah pengguna?

Sistem menyimpan foto referensi dan descriptor numerik 128 dimensi pada profil. Descriptor bukan gambar, tetapi tetap diperlakukan sebagai data biometrik sensitif.

4. Bagaimana menentukan wajah cocok?

Descriptor kamera dan descriptor profil dihitung Euclidean distance-nya. Implementasi menerima jika jarak maksimal 0,5. Nilai lebih kecil berarti lebih mirip.

5. Mengapa threshold 0,5?

Itu parameter implementasi yang cukup ketat untuk proyek, tetapi bukan angka universal. Penetapan terbaik harus dikalibrasi menggunakan dataset dan target FAR/FRR.

6. Apa beda face recognition dan liveness?

Recognition menguji kemiripan identitas. Liveness menguji respons gerakan terhadap challenge saat proses berlangsung. Keduanya menyelesaikan masalah yang berbeda.

7. Apakah foto atau video pasti tidak bisa lolos?

Tidak boleh diklaim pasti. Challenge acak dirancang mengurangi serangan foto/video sederhana, tetapi Tahap 1 masih berjalan di browser dan belum merupakan PAD tersertifikasi.

8. Mengapa memakai MediaPipe juga?

MediaPipe FaceLandmarker memberikan blendshape kedipan. Sinyalnya digabung dengan landmark face-api.js agar kedipan cepat lebih stabil di beragam perangkat.

9. Mengapa verifikasi wajah dilakukan dua kali?

Pemeriksaan awal memastikan orang yang memulai adalah pemilik akun. Pemeriksaan akhir memastikan wajah setelah menyelesaikan challenge tetap identitas yang sama.

10. Bagaimana arah kanan-kiri pada kamera depan?

Preview dicerminkan agar natural seperti cermin, tetapi analisis memakai frame asli. Karena itu instruksi dan mapping didefinisikan dari arah peserta, bukan sisi piksel yang terlihat pada layar.

Bagian 10.3

Latihan Pertanyaan Penguji II

11. Geolokasi menggunakan apa?

Koordinat diambil melalui HTML5 Geolocation API. Jarak dihitung dengan rumus Haversine di frontend untuk pre-check dan dihitung ulang oleh RPC database untuk keputusan akhir.

12. Mengapa lokasi laptop bisa salah?

Banyak laptop tidak memiliki GPS dan menggunakan estimasi Wi-Fi/IP. Opsi high accuracy hanya permintaan, bukan jaminan. Versi saat ini juga baru mengambil satu fix dan belum menilai coords.accuracy.

13. Apakah koordinat browser aman dari spoofing?

Tidak sepenuhnya. Server dapat menghitung ulang jarak, tetapi tidak dapat membuktikan sensor fisik tidak dipalsukan. Untuk ancaman lebih tinggi diperlukan kontrol tambahan seperti device attestation atau risk scoring.

14. Mengapa menggunakan waktu server?

Karena jam perangkat dapat salah atau dimanipulasi. Server memakai zona Asia/Jakarta untuk menentukan tanggal, waktu masuk, status, dan deadline secara konsisten.

15. Bagaimana mencegah absensi ganda?

Ada pengecekan RPC, unique index pada user dan tanggal, serta advisory lock untuk request bersamaan. Kombinasi ini menjaga invariant satu record per peserta per hari.

16. Bagaimana Alfa dibuat otomatis?

pg_cron memanggil fungsi pemeriksaan setiap menit. Fungsi membaca Jam Generate Alfa dinamis, memastikan hari kerja dan deadline sudah lewat, lalu memasukkan Alfa hanya bagi peserta aktif yang belum punya data.

17. Mengapa tidak menyimpan foto langsung di database?

File biner lebih sesuai disimpan pada object storage. Database menyimpan key/metadata, sehingga data transaksional tetap ringan dan akses file dapat diatur melalui signed URL.

18. Apa fungsi Edge Function?

Menjalankan operasi server yang membutuhkan secret atau hak tinggi, seperti akses R2, email persetujuan, cleanup storage, dan penghapusan user.

19. Apakah test yang ada membuktikan production aman?

Tidak. Contract test membuktikan pola dan aturan kode lokal. Production masih perlu verifikasi migration, RLS, Edge Function, browser nyata, dan konfigurasi remote.

20. Apa pengembangan paling penting berikutnya?

Mengukur akurasi secara formal dan memperbaiki akuisisi lokasi dengan beberapa sampel serta nilai accuracy. Setelah itu sinkronisasi schema production dan otomatisasi test/deploy.
